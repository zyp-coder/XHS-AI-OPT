## 第 1 章 产品定位与能力矩阵

### 1.1 定位

**一句话**：AI 驱动的多账号内容运营与评论区获客系统。

面向中小企业/个人博主，将"内容生产 → 发布 → 评论截流 → 私信转化 → 客户管理"全链路自动化，以 AI 大模型为决策核心、浏览器自动化为执行手段。

### 1.2 八大能力矩阵

| # | 能力 | 说明 |
|---|---|---|
| 1 | 账号管理 | 多账号扫码登录 + Cookie 持久化 + 登录状态轮询 |
| 2 | 内容生产 | AI 生成笔记/视频文案 + 按产品库批量生成 + 素材管理 |
| 3 | 定时发布 | Web 创建排期 → APScheduler → 浏览器自动发布 |
| 4 | 全场景截流 | 五场景雷达（latest/top/local/pain/highv）自动发现 → 爬坡判定 → AI 评论 → 活水清洗 |
| 5 | 评论获客 | 关键词截流 + 账号追踪 + 自营笔记自动回复 |
| 6 | 私信 CRM | 会话同步 + AI 意图分类 + 状态机 + 出站队列 + 快捷话术 |
| 7 | 账号诊断 | 品类检测 + 频率建议 + 选题清单 + 分阶段笔记规划 + 结构检查 |
| 8 | 数据分析 | 看板统计 + 趋势图 + AI 用量 + 引流趋势 |

### 1.3 双端形态

| 端 | 职责 | 技术 |
|---|---|---|
| **Web 后台管理端** | 策略配置 + 任务编排 + 数据看板 + AI Prompt 管理 | FastAPI + Alpine.js SPA |
| **Chrome MV3 扩展** | 就地执行 + DOM 抓取 + 实时 AI 辅助 + 私信同步 | Service Worker + Content Script |

两端通过 HTTP API（`127.0.0.1:8000`）通信，扩展亦可直连 LLM 服务商（双通道冗余）。

### 1.4 多租户与版本授权

- **多租户**：租户 = 产品。切换租户时整套配置（产品/AI/知识库/话术/Prompt/记录）完全隔离。
- **版本类型**（与 `build.js` PRESETS 对应）：
  - `dev`：开发版（全功能、永不过期，仅本地用）
  - `full`：全功能版（¥539/月，② + 线索）
  - `comment`：基础版（¥239/月，共有 + 发笔记；关键词不限量）
  - `comment-multi`：升级版（¥399/月，① + 获客；关键词不限量）
  - `pro`：自用版（全功能、零等待、永不过期，自用）
- **三档边界（2026-10-09 五十四改换盘，一条模块一条线、累进开通）**：共有＝账号诊断&配置 / AI 生成评论（含整页发送）/ 产品库·知识库 / 多产品切换 → ① 基础版＝共有 + 发笔记（含出片台）→ ② 升级版＝① + 获客 → ③ 全功能版＝② + 线索

### 2.5 关键设计原则

| 原则 | 实现 |
|---|---|
| 全局单例引擎 | `ai_engine` / `browser_engine` / `drain_engine` / `radar_engine` / `action_engine` / `wash_engine` / `scheduler` 均为模块级单例 |
| 延迟加载 | AIEngine 首次调用时才连接 LLM；BrowserEngine 首次任务时才启动浏览器 |
| lifespan 生命周期 | FastAPI lifespan 管理 init_db → scheduler.start → yield → browser.close → scheduler.stop |
| 双端解耦 | 扩展可独立运行（直连 LLM），也可与后端协作（HTTP API） |
| 数据本地化 | SQLite + 本地 Cookie，零云依赖 |

### 3.3 幂等迁移策略

`init_db()` 中使用 `ALTER TABLE ADD COLUMN` 模式实现幂等迁移：

```python
def init_db():
    Base.metadata.create_all(engine)  # 创建所有表（幂等）
    
    # 检查已有表的列，缺则 ALTER TABLE ADD COLUMN
    inspector = sa.inspect(engine)
    existing_cols = {c['name'] for c in inspector.get_columns('table_name')}
    if 'new_col' not in existing_cols:
        conn.execute(sa.text('ALTER TABLE table_name ADD COLUMN new_col TYPE'))
    
    # 播种默认 Prompt（upsert）
    # 播种默认 ScenarioConfig（仅不存在时插入）
```

这种模式保证：
- 新版本加字段时无需手动迁移脚本
- 多次启动不会报错
- 已有数据不受影响

### 6.1 AI 引擎（ai_engine.py）

**全局单例**：`ai_engine = AIEngine()`

#### 主备双模型热切换

```
主模型（免费/低价模型）
  ↓ 失败
判断 _should_fallback(error_msg)
  ↓ 命中关键词
备用模型（如 DeepSeek）
```

**触发 fallback 的关键词清单**：
- `insufficient_quota` / `rate_limit` / `quota` / `balance`
- `Unauthorized` / `invalid_api_key` / `Permission denied`
- `429` / `401` / `402`
- `Connection` / `timeout` / `connect` / `exceeded` / `limit`

#### Prompt 渲染流程

```
1. get_prompt(scene) → 从 DB 读取 system_prompt + user_prompt_template
2. _search_knowledge_base(context) → RAG 注入知识库
3. _search_script_library(context) → 角色话术注入
4. 占位符替换：context 中的 key → {key} 替换到 user_prompt_template
5. 返回 (system, user) 元组
```

#### RAG 知识库注入逻辑

1. **常驻加载**：`category IN ("个人经历", "产品介绍")` 的前 10 条
2. **上下文搜索**：从 context 提取 note_title/comment_content/note_content 拼接为搜索词，LIKE 匹配 title/content/tags，取最近更新的 8 条
3. **注入格式**：
```
【知识库参考信息】
- 标题1: 内容1(截取前200字)
- 标题2: 内容2 [截图: url]
...

【重要——你必须引用上面的知识库】以上知识库有大量真实产品数据...
你的回复必须从中提取具体的数字、事实、案例来支撑你的观点。
```

## 第 7 章 五场景全场景截流系统（核心特色）

> 模型口径（2026-09-22 定稿）：**一个关键词 × 不同搜索筛选 → 不同类型的笔记**，每类笔记各有自己的评论方式与维护节奏。
> 前四类由关键词派生（latest/top/local/pain），highv 走白名单主页、是另一套逻辑（延后做）。

### 7.1 五场景总览表

| 场景 | 入列来源 | 采集频率 | 爬坡判据 | 目标评论数 | 存活期 | 活水周期 | 退出机制 |
|---|---|---|---|---|---|---|---|
| latest 最新笔记 | 关键词搜索「最新」 | 5分钟 | Δ点赞≥50 | 1条 | 24h | 24h | 到期/连续3次无爬坡 |
| top 搜索TOP笔记 | 关键词搜索「点赞/评论/收藏最多」 | 30分钟 | 长期驻留 | 3条(上限5) | 永久 | 7天 | 连续5次无爬坡/掉出前排2周 |
| local 本地笔记 | 关键词+属地搜索「最新」 | 10分钟 | 入列即评论 | 1条 | 24h | 24h | 到期/连续3次无爬坡 |
| pain 求助笔记 | 求助关键词命中 | 15分钟 | 入列即触发 | 1条(上限2) | 48h | 24h | 到期/连续3次无爬坡 |
| highv 高V狙击 | 白名单最新内容 | 15分钟 | 热评存在 | 3条 | 永久 | 12h | 连续4次无爬坡/掉位1周 |

### 7.2 各场景详细说明

#### latest — 最新笔记（抢新笔记前排）

- **目标**：关键词「最新」流里刚起飞的笔记，起飞前 10 分钟抢到前排评论 C 位
- **发现**：按活跃关键词搜索最新内容（排序选「最新」）
- **爬坡**：相邻两次快照的点赞增量 ≥ climb_likes_delta（默认50）
- **评论策略**：1条干货钩子评论，40-60字，观点鲜明
- **存活期**：24小时（到期自动退出）
- **活水**：24小时后审查，0赞→删+重发
- **Prompt 场景**：`latest_comment`

#### top — 搜索TOP笔记（霸占搜索排名）

- **目标**：在搜索流量 TopN 的老内容下长期占据高质量评论位
- **发现**：按关键词搜索「点赞最多/评论最多/收藏最多」（默认前20），已在列的更新卡位
- **爬坡**：无爬坡判据（长期驻留型），按活水周期复审我的评论位置
- **评论策略**：3条目标（上限5条），80-150字极度专业方案评论
- **存活期**：永久（entry_ttl_hours=-1）
- **活水**：每7天复审，0赞→删+重发
- **退出**：连续被挤出前排 2 周→淘汰
- **Prompt 场景**：`top_comment`

#### local — 本地笔记（抓属地本地流量）

- **目标**：借本地信任感截流同城刚需用户
- **发现**：按关键词+属地搜索最新内容（region_hint 注入城市/区名）
- **爬坡**：入列即评论（不看热度）
- **评论策略**：1条，注入地域信任词（"同在XX区""我家就住XX附近"），40-60字
- **存活期**：24小时
- **Prompt 场景**：`local_comment`

#### pain — 求助笔记（精准转化求助用户）

- **目标**：命中求助意图的精准用户，给针对性解决路径
- **发现**：按 intent_keywords 搜索，标题命中关键词才入列
- **默认关键词**：求推荐/听劝/怎么办/求建议/求助/避雷/怎么选
- **爬坡**：入列即确认意图（首次快照后直接触发）
- **评论策略**：1-2条，50-90字，共情+具体解决步骤
- **存活期**：48小时
- **Prompt 场景**：`pain_comment`

#### highv — 高V狙击（借头部IP溢出流量）

- **目标**：在头部博主评论区借溢出流量被大家看到
- **发现**：从白名单 TargetAccount 取每人最新一篇内容
- **爬坡**：`hot_comment_top()` 存在热评（说明评论区活跃）
- **评论策略**：3条，60-100字，"极度赞同+补充干货"降维打击
- **存活期**：永久
- **活水**：12小时审查
  - 已爆（赞≥50 或 回复≥10）→ **主动撤换钩子**（删+换新话术重发）
  - 死评论（0赞）→ 删+重发
  - 存活 → 保留
- **退出**：连续掉位1周
- **Prompt 场景**：`highv_comment`

### 7.3 状态机

#### MonitorState（监控状态）

```
monitoring → actioned → expired → archived
    │                        ↑
    └────────────────────────┘ (未触发直接过期)
```

#### ExitReason（退出原因）

| 值 | 含义 | 触发条件 |
|---|---|---|
| time_expired | 监控期到期 | now >= expire_at |
| no_potential | 判死退出 | consecutive_no_climb >= no_climb_strikes |
| goal_done | 达成退出 | 成单/已爆撤换 |
| replaced | 让位退出 | consecutive_off_rank_weeks >= exit_wait_weeks |

#### WashStatus（活水状态）

```
pending → dead → reposted
       → active_removed
       → kept
```

## 第 10 章 消息中心（私信 CRM）

### 10.1 核心设计原则

1. **AI 只打标不筛选**：所有会话一律保留可见，AI 只做标签（intent 意图 + label 有效/待定/待复核），不自动删除/隐藏
2. **时间驱动状态**：对方刚回 → 销售中；N天无互动 → 需跟进；达流失阈值 → 建议流失（人工确认）
3. **扩展-后端协作**：扩展负责从平台抓取 + 真实发送；后端负责存储 + diff + AI 分析 + 队列管理

### 10.4 状态机（6 态）

```
                 ┌──────────────────────────────────────┐
                 │                                      │
  ┌──────────┐   │   ┌──────────┐   ┌──────────┐       │
  │ chunting │───┼──▶│ selling  │──▶│   won    │──┐    │
  │ (初触)   │   │   │ (销售中) │   │ (已成交) │  │    │
  └──────────┘   │   └──────────┘   └──────────┘  │    │
       │         │        │                        ▼    │
       │         │        │              ┌──────────────┐│
       │         │        ▼              │  completed   ││
       │         │   ┌──────────┐       │ (已完成/复购) ││
       │         │   │ followup │       └──────────────┘│
       │         │   │ (需跟进) │                        │
       │         │   └──────────┘                        │
       │         │        │                              │
       ▼         │        ▼                              │
  ┌──────────┐   │   ┌──────────┐                       │
  │   lost   │◀──┴───│   lost   │                       │
  │ (流失)   │       │ (流失)   │                       │
  └──────────┘       └──────────┘                       │
       │                                                 │
       └─── 复活（对方又回话）→ 清除 lost_at ────────────┘
```

| 状态 | 值 | 说明 |
|---|---|---|
| 初触 | chunting | 我方先触达，对方未回复 |
| 销售中 | selling | 对方刚回话（激活窗口内） |
| 已成交 | won | 人工标记成交 |
| 已完成 | completed | 成交后服务完毕/可复购 |
| 需跟进 | followup | N 天无推进（规则触发） |
| 流失 | lost | 达流失阈值（规则触发，人工确认） |

### 10.5 激活/流失机制

#### 可配置参数（`/api/messages/settings`）

| 参数 | 默认值 | 说明 |
|---|---|---|
| msg_active_days | 3 | 对方回话且最后活跃在 N 天内 → 视为激活 → 建议"selling" |
| msg_followup_days | 5 | N 天无互动 → 建议"followup" |
| msg_lost_days | 10 | N 天无互动 → 建议"lost" |
| msg_label_enable | "1" | 是否启用 AI 标签 |

#### 状态建议逻辑（_suggest_status）

```python
# 已终态(won/completed/lost)不再建议
if cur in ("won", "completed", "lost"): return

# 对方刚回(激活窗口) → selling
if them_just_replied and inactive <= active_days: suggest("selling")

# 流失机制：达到阈值且非 selling
elif inactive >= lost_days and cur != "selling": suggest("lost")

# 需跟进
elif inactive >= followup_days: suggest("followup")
```

#### 复活机制

- 对方又回话（`them_replied=True` 且 `last_from="them"`）→ 清除 `lost_at`
- 下次 sync 时 `_apply_loss()` 自动执行

### 10.7 扩展 ↔ 后端同步协议

#### 同步流程

```

    │
    ▼
POST /api/messages/sync {product, items: [{conv_id, partner_name, last_msg, last_at, ...}]}

    │ 打开完整聊天 → 抓取消息时间线
    ▼

    │ 后端去重(xhs_msg_id) → 有新对方消息 → 触发 _classify() + _suggest_status()

```

#### 区间随机机制

```javascript
// 支持两种格式：
// 旧：{key: 数值}  → min=值, max=值×1.6
// 新：{key: {min, max}} → 区间内均匀随机
function dwellMs(key, floor) {
  const c = _delayCfg[key];
  let minV, maxV;
  if (typeof c === 'object') { minV = c.min; maxV = c.max; }
  else { minV = maxV = c; maxV = Math.round(maxV * 1.6); }
  return Math.max(floor, minV + Math.random() * (maxV - minV));
}
```

#### 完整性签名（FNV-1a）

```javascript
function fnv1a(str) {
  let h = 0x811c9dc5;
  for (let i = 0; i < str.length; i++) {
    h ^= str.charCodeAt(i);
    h = Math.imul(h, 16777619);
  }
  return (h >>> 0).toString(16);
}

// 签名载荷 = JSON.stringify({type, licensee, builtAt, expireAt, boundAccount, features})
// 签名值存在 EDITION._sig
// 校验：Edition.integrityOk() → fnv1a(载荷) === EDITION._sig
```

#### 授权检查流程

1. `Edition.integrityOk()` — 签名校验（防篡改）
2. `Edition.hasBinding()` — 是否有账号绑定
3. `Edition.boundXhsId()` — 返回绑定的平台账号
4. 剩余天数 = `(expireAt - now) / 86400000`
5. 绑定验证：content script 在本人主页读取实际账号 → 对比绑定号 → 写入缓存（6h TTL）

## 第 12 章 浏览器自动化细节

### 12.1 Playwright 单例（仅 Android 模拟器模式）

#### 设计原则

- **全局单例**：整个后端只维护一个 `BrowserEngine` 实例
- **只跑真实设备**：Playwright 经 CDP 接入 Android 模拟器里的真实 Chrome 操作页面；不做桌面浏览器伪装，不改写浏览器指纹
- **不做桌面兜底**：模拟器启动失败直接返回 `error:...`，由调用方提示用户，不降级到桌面 Chromium

#### 启动模式

```
EMULATOR_ENABLED?
├── Yes → _start_avd_mode()        # 启动 Google AVD
└── No → 返回 error:模拟器模式已禁用
```

启动成功后：`status="running"` → 按 account_id 加载 Cookie → 启动 60 秒心跳健康检查。

### 12.2 Android 模拟器路径

#### 配置项（config.py）

| 配置 | 默认值 | 说明 |
|---|---|---|
| EMULATOR_ENABLED | True | 是否启用模拟器模式 |
| AVD_NAME | xhs_phone | AVD 虚拟设备名 |
| AVD_DEVICE | pixel_6_pro | AVD 设备型号 |
| ANDROID_SDK_ROOT | ~/AppData/Local/Android/Sdk | Android SDK 路径 |

#### Google AVD 流程

```
1. _find_adb()（编排器 _start_emulator_mode）→ PATH / Android SDK 目录
2. 检查 AVD 目录存在（~/.android/avd/{name}.avd）
3. 检查是否已有模拟器在运行（adb devices → emulator-5554），已启动则复用
4. 若无 → 启动 emulator.exe：
   -avd {name} -no-snapshot -gpu host -no-audio -memory 3072 -netdelay none -netspeed full
5. _wait_for_boot() → 轮询 sys.boot_completed + pm path android
6. _configure_emulator() → 语言 zh-CN + 时区 Asia/Shanghai + 移动网络
7. _connect_chrome_cdp():
   a. 检查 Chrome 安装（pm list packages com.android.chrome）
   b. am start 启动 Chrome
   c. adb forward tcp:9222 localabstract:chrome_devtools_remote
   d. _wait_for_cdp() → 轮询 /json/version 直到就绪
   e. playwright.chromium.connect_over_cdp("http://127.0.0.1:9222")
```

#### 模拟器健康管理

- 每 60 秒检查：进程是否存活 + adb ping + CDP 连接
- 异常时标记 `status="crashed"`
- 自动尝试重连 CDP

```python
def _start_health_check(self):
    async def _health_loop():
        while True:
            await asyncio.sleep(60)
            # 1. 模拟器模式：检查进程/adb/CDP
            if self._emulator_mode:
                if not await self._check_emulator_health():
                    self.status = "crashed"
                    continue
            # 2. 常规模式：检查页面存活
            alive = await self._is_page_alive()
            if not alive:
                self.status = "crashed"
            elif self.status == "crashed":
                self.status = "running"  # 自动恢复
    self._health_task = asyncio.create_task(_health_loop())
```
