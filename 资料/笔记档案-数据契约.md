# 笔记档案 · 数据契约（2026-10-08 起冻结稿）

> 真源：`extension/popup.js` 的 `npNotesAll()` / `npArchiveSave()` / `npArchiveData()`
> 落盘 key：`np_notes`（chrome.storage.local）
> demo 镜像：`tmp/三方向demo.html` 的 `rows[]` / `mkRow()`
> 适用范围：所有发笔记模块（写文案 / 造图片 / 出片台 / 素材库 / 发布台 / 复盘分析）一律按此契约读写真档。
>
> 本文档冻结于本次（三方向 demo 落地后）落扩展的起点。改字段先改文档再改代码；改代码不改文档 = bug。

### 1.6 **【新加】方向字段**（demo 9 篇都有，真实 entry 没记）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `dir` | enum | ✓ | `k` / `d` / `c` / `''`（老路=空） |

## 二、status 状态机

```
草稿(0) → 代发(1) → 已发(2) → 已归档(3)
   ↓          ↓
  撤回 = 已发 → 代发（行内状态下拉）
```

**二十八改改口（2026-10-09）**：状态词「待发」全站改名「**代发**」——`NP_AR_STATUS = ['草稿','代发','已发','已归档']`；`NP_AR_RANK` 保留 `'待发':1` 同一位兜底老数据；读时由 `npArchiveCoerce` 归一 `'待发' → '代发'`（单一入口），手动改状态（`npNoteSetStatus`）与各「进代发」写盘点同样兼容老词，写回后落盘即新词。

约束：
- 只许往前推：`NP_AR_RANK[forceStatus] > NP_AR_RANK[cur]` 才更新；用户标过「已发」再来一次定稿不该被拖回「代发」
- 状态切换时 `statusAt[status] = Date.now()` 一定要写（复盘分析算日均赞靠它）
- 行内状态下拉 = 唯一入口；老的「🔎 认领：我发了哪些」面板已下线（五十三改）

## 三、存储与并发

### 3.1 存盘 key 与上限

- key = `np_notes`（chrome.storage.local 单 key 存整份 Array）
- 上限 = 300（NP_NOTES_CAP）
- 超上限丢弃顺序：先丢最旧的「已归档」→ 再丢最旧的「已发」→ 最后才动别的；刚写的永远不丢（npNotesTrim）

### 3.2 串行写

`_npArChain` 串行化所有写操作（npNotesSync）：
- 「读整条 → 改 → 写整条」模型
- 两笔并发会互相覆盖丢档 = 用户一眼看得见的损失
- 真扩展就这么做，demo 内存版不用

### 3.3 派生多平台（48/52 改）

📕 xhs = 原始档；其余平台各改写一版 = **各成一档**：
- 派生档 `origin='derive'`、`derivedFrom=源 id`、`derivedFromTitle=源标题`
- 派生档 `platform≠xhs`、`form` 同源、`filmKind` 各自独立
- 派生档各自标发布状态、料各自造、写挂各自重试
- 底稿以后改 = 旧派生版统一失效重写（按 verSeed 指纹判断）

—— 落扩展存储：派生档全存在 `np_notes` 同 key、靠 `derivedFrom` 字段分组；列表展示时同行 = 派生关系。

## 五、改这张契约要走的事

1. 改字段 → 先改本文档 → 改 `extension/popup.js` 的 `npArchiveData` / `npArchiveSave` / `npNotesTrim` 三个函数
2. 加新字段 → 同步：
   - `npArchiveHasWork` 判存盘条件
   - `npNotesTrim` 丢弃策略（如果新字段影响"刚写的"判定）
   - `nparRowHtml` 列展示
   - `npPlanItemPayload` 排产表同步（如 `dir` / `kOut` 影响 planItem）
3. 加 demo 字段 → 同步：demo 的 `mkRow` / `rows[]` 种子、`openWB` 兜底回填、`rowNext` 状态机
4. 加 schema version → 写 `np_notes_schema` 这个 key 存版本号；老版本升级时跑一次迁移函数
